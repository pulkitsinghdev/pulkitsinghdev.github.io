# Project submission checklist

Use this checklist for every project you want featured. You do not need to prepare a polished case study yourself; send what you have and I can inspect the repository, help fill gaps, and write the final portfolio copy.

## Essential information

1. **Project name** — the exact name you want displayed.
2. **One-line description** — what it does, in plain language.
3. **Problem and users** — what problem it addresses and who it is for.
4. **Your role** — solo/team project, team size, your specific contribution, and which parts you personally implemented.
5. **Current status** — prototype, in progress, completed, deployed, archived, or contributed to. Include dates or duration if useful.
6. **Technology stack** — languages, frameworks, databases, infrastructure, APIs, models, and tools actually used. Separate technologies used from technologies only planned.
7. **Main features** — the 3–6 most important capabilities that currently work.
8. **Technical depth** — architecture, data flow, APIs, algorithms, infrastructure, important engineering decisions, trade-offs, and difficult bugs solved.
9. **Evidence and links** — GitHub repository, live demo, documentation, Devpost/project page, relevant PRs/issues, or a short demo video.

## Visual material

Send any available material; not every item is mandatory:

- 3–6 clear screenshots of the actual product (desktop or mobile, preferably full-resolution).
- A 30–90 second screen recording or demo video, especially for interactive projects.
- Architecture diagram, sequence diagram, database schema, or API diagram when relevant.
- Terminal output, benchmark graphs, dashboards, or test reports when they provide meaningful proof.
- A logo or project mark only if you already have one.

Please do not send generated mockups as though they were real product screenshots. If the project has no UI, use architecture diagrams, terminal captures, logs, or a clear technical illustration instead.

## Results and proof

Share measurable results only when you can substantiate them: users, requests handled, latency, throughput, test coverage, benchmark comparisons, contributors, merged PRs, uptime, or adoption. Include the measurement method and timeframe where possible. If there are no metrics, that is fine; we can explain the engineering work without inventing numbers.

## Team and open-source details

For group projects, identify your exact contribution and the work done by teammates. For open-source contributions, provide repository links and specific PRs, issues, commits, releases, or maintainership responsibilities. Mention licenses and third-party assets where applicable.

## What not to share

- API keys, passwords, access tokens, private certificates, or `.env` files containing secrets.
- Private user data, production credentials, or confidential employer/client information.
- Claims, metrics, roles, or features that cannot be verified.

## What makes a project portfolio-ready

A strong entry should let an engineer or recruiter understand the problem, inspect the implementation, see what you personally built, and evaluate the technical decisions. A real repository with a clear README, reproducible setup, meaningful commits, tests, and a working demo is more valuable than a visually polished but unverifiable project card.
